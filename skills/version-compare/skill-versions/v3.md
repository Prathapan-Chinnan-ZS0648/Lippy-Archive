# Version compare

This skill judges what changed between versions of a document. It is organized as
independent modules so a user of this skill can apply, extend, or override one module
(e.g. domain guidance for a new document type) without touching the others. Nothing in
Modules 2–6 may contradict Module 1 (Core rules) — they specialize how Module 1 is
applied, they do not replace it.

---

## Module 1 — Core rules (invariant across every use of this skill)

These rules do not change per document type, domain, or format. They are what "changed",
"added", "removed", and "unchanged" mean, full stop.

### The five verdicts

Begin every finding with exactly one of these five words, then a dash, then the detail:

**CHANGED**, **ADDED**, **REMOVED**, **UNCHANGED**, or **NOT ADDRESSED**.

After the word, show both sides in the same sentence — what the unit was and what it
became, each figure quoted exactly as its document writes it — "Net 30" where the
document says Net 30, never "net thirty" — because a reworded figure can no longer be
found in the source and a report that cannot be matched against its documents cannot be
checked. "CHANGED — the cap was twelve months of charges and is now three months" is a
finding. "CHANGED" on its own is a claim the reader has to take on trust, and a change
report nobody can check is worse than none because it will be believed anyway.

Each passage you are shown is labelled with the document it came from. That label is what
tells you which version you are looking at, and it is the whole basis of the comparison. A
unit present in the older document and absent from the newer one is REMOVED — say so and
quote the old wording. A unit in the newer one only is ADDED.

**No verdict from one side.** Every verdict is a claim about both documents, so it needs
evidence from both. UNCHANGED asserted from one version's passage alone claims the other
version says the same thing without having seen it. REMOVED needs two things at once: the
unit's own wording quoted from the older document, and the newer document searched with
nothing matching — a passage's absence from what you were shown is not its absence from
the document. A REMOVED whose quote is the question's words rather than the document's is
a fabrication. When only one side is in evidence and the other was not searched empty, the
honest answer is NOT ADDRESSED — the comparison could not locate the unit, which is a
different fact from any of the four verdicts.

Each unit of the newer version is set against the older one. The verdict says which of the
four things happened, and every verdict that is not UNCHANGED shows **both sides** — the
old wording and the new — so the reader can see the change rather than take it on trust.

**Unchanged is a finding.** A comparison that lists only what moved leaves the reader
unable to tell "this unit is identical" from "this unit was not examined", and those are
very different facts when the document controls an obligation, a price, or a right. Every
unit examined appears, including the ones that did not move.

A unit in the old version with no counterpart in the new is **REMOVED**, and it appears
with its old text and nothing opposite it. This is the case a diff of the new document
against itself can never surface, and removals are usually the changes that matter most.

**Granularity does not change what ADDED/REMOVED mean.** The rule applies exactly the
same way whether the unit with no counterpart is one clause, an entire subsection, a
whole section (even one whose number or heading slot persists with different or emptied
content), or an entire top-level unit of the document (e.g. one sheet of a workbook, one
slide of a deck) with no corresponding unit at all. Judge every clause within a
larger-scope addition or removal individually, per this same rule — never as one
aggregate verdict for the whole unit — so the report still shows each clause's own
evidence rather than a single unverifiable claim covering many.

**This skill describes what changed. It does not evaluate the change.** It does not say
whether the change is good, who benefits, or what to do about it — those are judgements
about position or consequence, and nothing in the documents themselves supports them.
World knowledge may not be used to fill that gap.

## Module 2 — Workflow (the reusable processing pipeline)

These stages apply to any pair (or set) of document versions, in any format. A specific
domain (Module 3) may add detail inside a stage but may not skip or reorder them.

| # | Stage | What happens | Notes |
|---|---|---|---|
| 1 | UNDERSTAND | Determine this document's **grain** — the atomic unit that gets one verdict each (a clause, a control, a table row, a form field, a code line, a numbered provision, a line item — see Module 3 for how to choose). Determine whether the documents share a common structure (same section order/names) or must be aligned by content. | Grain must be fixed *before* comparison starts and stated in the run's config, so a reviewer can tell what was and wasn't compared. |
| 2 | MAP | Build a mapping from each unit in the newer document to its counterpart (if any) in the older document, and note any older unit with no counterpart in the newer one. Map by **content/label, not by position, ID, or presentation format** — a renumbered, reordered, relettered, or reformatted unit (e.g. prose rewritten as a table row) is still the same unit if its subject matter matches; a same-numbered or same-format unit with different subject matter is a different unit. Do not defer to a document's own stated claim about the relationship between two units (e.g. "replaces," "supersedes") — verify that claim against the two units' actual content before accepting it. | This is what makes REMOVED and ADDED detectable even when a document inserts or deletes rows partway through a numbered sequence, changes a unit's presentation format, or asserts a relationship between units that does not hold up against their actual wording. See edge cases "Row/ID renumbering" and "A document's own stated relationship between units" in Module 6. |
| 3 | RETRIEVE | For each mapped (or unmapped) unit, retrieve the exact wording from each document it appears in. | Retrieval must come from the document itself (or its normalized twin), never from memory of a similar unit seen elsewhere. |
| 4 | JUDGE | Apply Module 1's verdict rules to each unit using only what was retrieved. | No verdict without evidence from both sides, per Module 1. |
| 5 | VALIDATE | Run the Module 4 checklist before treating any output as final. | Catches the most common failure modes before they reach a reader. |
| 6 | REPORT | Assemble the output per Module 5. | — |

A document set with no shared structure at all (e.g. comparing a policy document against
a completely differently organized successor) still follows this pipeline — stage 1's
"map by content" becomes the primary tool, since there is no positional or named
structure to lean on.

## Module 3 — Domain guidance (how to choose the grain, applied per document type)

This module is illustrative, not exhaustive, and never overrides Module 1. Its only job is
to help stage 1 (UNDERSTAND) pick a sensible grain for a document type this skill has not
seen before. When a new document type doesn't fit any row below, choose the smallest unit
that carries one independent obligation, fact, or value, and add a row here once the
choice has been validated on real input (see `bootstrap.md` §8.2, the promotion bar — this
table itself only grows through that mechanism, not by editing it freely per sample).

| Document type | Suggested grain | Why |
|---|---|---|
| Contracts, RFPs, policies, terms & conditions | One clause or numbered provision | Each clause typically carries one independent obligation or fact. |
| Checklists, certification forms | One line item, kept **distinct** from any requirement it certifies elsewhere in the document | A checklist line can be removed while the requirement it certifies remains stated elsewhere — these are two different units, not one (see Module 6). |
| Tabular data, pricing schedules, financial statements | One row, or one cell if rows carry multiple independently-changeable values | Compare by row label/content, not row position — see Module 2 stage 2 and Module 6. |
| Structured/technical specifications (API contracts, schemas, configs) | One field, parameter, or key-value pair | Mirrors how such documents are actually versioned and diffed by their own tooling. |
| Source code or scripts | One logical statement or block, not one line of raw text | A reformatted-but-semantically-identical line should not read as CHANGED merely because whitespace moved — but this skill does not resolve semantic equivalence beyond exact-text comparison; if the domain requires it, that judgment is a documented deviation (`Manifest.md`), not a silent skill behavior. |
| Narrative/prose documents (reports, manuals) without clause numbering | One paragraph or one sentence, chosen consistently for the whole document | Consistency of grain across the whole document matters more than which exact size is chosen. |

If the two documents being compared are different formats (e.g. a PDF contract against a
Word amendment, or a spreadsheet against a PDF-rendered version of the same data), extract
both into the same normalized text form before applying the grain — comparison happens on
the extracted content, not on file-format-specific rendering.

## Module 4 — Validation and quality checks

Run this checklist before treating any comparison as finished. Each item traces back to a
Module 1 rule.

- [ ] Every unit in scope has exactly one verdict — none skipped, none double-counted.
- [ ] Every non-UNCHANGED verdict shows both sides' exact wording (or explicitly shows only
      one side plus a statement that the other side was searched and found empty, for
      ADDED/REMOVED).
- [ ] No verdict was assigned from evidence in only one document (Module 1, "No verdict
      from one side").
- [ ] NOT ADDRESSED was used only where the unit could not be located after an active
      search of both documents — never as a stand-in for "I didn't check."
- [ ] Units were mapped by content/label, not by position or numbering, per Module 2 stage
      2 — re-verify this explicitly wherever the document set renumbers or reorders units
      between versions.
- [ ] If either document self-annotates its own changes (markers, tracked changes,
      revision bars), those annotations were used only as a cross-check, never as the sole
      basis for a verdict — see Module 6.
- [ ] The grain chosen in stage 1 was applied consistently across the whole document, not
      loosened or tightened partway through.
- [ ] No commercial, legal, or operational judgment about the change appears in the
      findings — only what changed, per Module 1's closing rule.

## Module 5 — Output requirements

One row per unit: what it was, what it became, and which of the five verdicts applies.
Grouped by the document's own structure (sections, sheets, tables) where one exists, in
that structure's order; grouped by topic or content-similarity where no shared structure
exists.

Nothing is reported as changed, added, or removed without the evidence Module 1 requires
shown alongside it. A change asserted with only one side visible is unverifiable, and an
unverifiable change report is worse than none because it will be believed.

A finished comparison also states, at minimum: a count of units per verdict, and — where
the comparison surfaces something a reader would otherwise have to infer (an absence with
no marker, a checklist/requirement split, a structural mismatch between documents) — an
explicit call-out, per Module 6.

## Module 6 — Edge-case handling

Cases this skill has been confirmed to handle correctly, generalized from evidence across
processed samples (see `skills/version-compare/pattern-log.md` for the promotion history
behind each row). This module grows only through the promotion bar in `bootstrap.md`
§8.2 — never by editing a rule to fit one sample's specifics.

| Edge case | Handling |
|---|---|
| Self-annotation (a document marks its own additions/changes, e.g. with bracketed tags or tracked changes) | Use the annotation only as a cross-check pointer to where to look closely. Every marked *and* unmarked unit still gets independently compared against both documents' actual text per Module 1 — the annotation is never the sole basis for a verdict, since it may be incomplete (e.g. it may mark additions but not removals). |
| Row/ID renumbering (inserting or deleting a row shifts the numeric/lettered IDs of unrelated rows below it) | Map and compare units by content/label, not by their positional ID or number — see Module 2 stage 2. A row that only moved position is UNCHANGED, not CHANGED. |
| Checklist/certification line vs. the requirement it certifies | These are two distinct units even when adjacent or textually similar. A checklist line can be REMOVED while the underlying requirement remains UNCHANGED elsewhere in the document — judge each independently; do not assume they move together. |
| Absence with no annotation marker | An annotation scheme that marks additions/changes does not necessarily mark removals. Absence is detected by actively searching the newer document for the older unit's content and confirming nothing matches — never by the absence of a removal marker alone. |
| No shared structure between documents, or an otherwise-matching structure with one unit missing entirely | When the two versions do not share section names, numbering, or layout, Module 2 stage 2's content-based mapping is the *only* tool — do not assume a 1:1 structural correspondence. This applies just as much when most of the structure *does* match and only one top-level unit (a section, a sheet, a slide) has no plausible counterpart at all — that unit's clauses are ADDED or REMOVED per Module 1's granularity-agnostic rule, not forced into an unrelated pairing with a differently-named unit just because the two document sets otherwise line up. |
| A unit's slot persists but its content is emptied or replaced, distinct from the unit having no slot at all | A section/unit can keep the same number, heading, or position across versions while every substantive clause inside it is removed and replaced with placeholder or explanatory text (e.g. "this section has been removed; see the governing agreement"). Judge each of the old clauses REMOVED individually and any new explanatory text ADDED — do not treat the persisting slot as evidence the content is UNCHANGED, and do not treat this the same as the unit being absent outright (the row above) — the two are different facts about the document set. |
| A document's own stated relationship between two units (e.g. "replaces," "supersedes," "restates") | Never accept a document's own characterization of how one unit relates to another as authoritative. Map both units by content independently first (Module 2, stage MAP); only report the relationship the content actually supports. A unit stated to "replace" another may in fact be REMOVED + ADDED (two independent, substantively different units) rather than one CHANGED unit, if their actual wording does not describe the same obligation. |
| Multiple supporting/reference documents, or more than two versions | Apply the same pairwise logic between each version and its immediate predecessor (or against whichever version the run's config designates as the baseline for that unit); do not merge multiple documents' evidence into a single verdict without stating which document each side of the quote came from. |
| Mixed or converted formats (PDF vs. Word vs. spreadsheet vs. plain text) | Normalize both documents to extracted text (per the run's `actuals/twin/` process) before applying grain and verdicts — comparison operates on that normalized text, not on format-specific rendering artifacts. Confirmed in practice across PDF and spreadsheet (`.xlsx`) samples; this row requires no per-format skill logic, only a format-appropriate twin-extraction unit (a page, a sheet, a slide, a row) chosen at the orchestration layer, per `bootstrap.md` §1/§12. |
