## Module 2 — Workflow (the reusable processing pipeline)

A specific

| # | Stage | What happens | Notes |
|---|---|---|---|
| 1 | UNDERSTAND | Determine this document's **grain** — the atomic unit that gets one verdict each (a clause, a control, a table row, a form field, a code line, a numbered provision, a line item — see Module 3 for how to choose). Determine whether the documents share a common structure (same section order/names) or must be aligned by content. | Grain must be fixed *before* comparison starts and stated in the run's config, so a reviewer can tell what was and wasn't compared. |
| 2 | MAP | Build a mapping from each unit in the newer document to its counterpart (if any) in the older document, and note any older unit with no counterpart in the newer one. Map by **content/label, not by position, ID, or presentation format** — a renumbered, reordered, relettered, or reformatted unit (e.g. prose rewritten as a table row) is still the same unit if its subject matter matches; a same-numbered or same-format unit with different subject matter is a different unit. Do not defer to a document's own stated claim about the relationship between two units (e.g. "replaces," "supersedes") — verify that claim against the two units' actual content before accepting it. | This is what makes REMOVED and ADDED detectable even when a document inserts or deletes rows partway through a numbered sequence, changes a unit's presentation format, or asserts a relationship between units that does not hold up against their actual wording. See edge cases "Row/ID renumbering" and "A document's own stated relationship between units" in Module 6. |

| Document type | Suggested grain | Why |
|---|---|---|
| Contracts, RFPs, policies, terms & conditions | One clause or numbered provision | Each clause typically carries one independent obligation or fact. |
| Checklists, certification forms | One line item, kept **distinct** from any requirement it certifies elsewhere in the document | A checklist line can be removed while the requirement it certifies remains stated elsewhere — these are two different units, not one (see Module 6). |
| Tabular data, pricing schedules, financial statements | One row, or one cell if rows carry multiple independently-changeable values | Compare by row label/content, not row position — see Module 2 stage 2 and Module 6. |
| Structured/technical specifications (API contracts, schemas, configs) | One field, parameter, or key-value pair | Mirrors how such documents are actually versioned and diffed by their own tooling. |
| Source code or scripts | One logical statement or block, not one line of raw text | A reformatted-but-semantically-identical line should not read as CHANGED merely because whitespace moved — but this skill does not resolve semantic equivalence beyond exact-text comparison; if the domain requires it, that judgment is a documented deviation (`Manifest.md`), not a silent skill behavior. |
| Narrative/prose documents (reports, manuals) without clause numbering | One paragraph or one sentence, chosen consistently for the whole document | Consistency of grain across the whole document matters more than which exact size is chosen. |

## Module 6 — Edge-case handling

behind each row).

| Edge case | Handling |
|---|---|
| Self-annotation (a document marks its own additions/changes, e.g. with bracketed tags or tracked changes) | Use the annotation only as a cross-check pointer to where to look closely. Every marked *and* unmarked unit still gets independently compared against both documents' actual text per Module 1 — the annotation is never the sole basis for a verdict, since it may be incomplete (e.g. it may mark additions but not removals). |
| Row/ID renumbering (inserting or deleting a row shifts the numeric/lettered IDs of unrelated rows below it) | Map and compare units by content/label, not by their positional ID or number — see Module 2 stage 2. A row that only moved position is UNCHANGED, not CHANGED. |
| Checklist/certification line vs. the requirement it certifies | These are two distinct units even when adjacent or textually similar. A checklist line can be REMOVED while the underlying requirement remains UNCHANGED elsewhere in the document — judge each independently; do not assume they move together. |
| Absence with no annotation marker | An annotation scheme that marks additions/changes does not necessarily mark removals. Absence is detected by actively searching the newer document for the older unit's content and confirming nothing matches — never by the absence of a removal marker alone. |
| No shared structure between documents, or an otherwise-matching structure with one unit missing entirely | When the two versions do not share section names, numbering, or layout, Module 2 stage 2's content-based mapping is the *only* tool — do not assume a 1:1 structural correspondence. This applies just as much when most of the structure *does* match and only one top-level unit (a section, a sheet, a slide) has no plausible counterpart at all — that unit's clauses are ADDED or REMOVED per Module 1's granularity-agnostic rule, not forced into an unrelated pairing with a differently-named unit just because the two document sets otherwise line up. |
| A unit's slot persists but its content is emptied or replaced, distinct from the unit having no slot at all | A section/unit can keep the same number, heading, or position across versions while every substantive clause inside it is removed and replaced with placeholder or explanatory text (e.g. "this section has been removed; see the governing agreement"). Judge each of the old clauses REMOVED individually and any new explanatory text ADDED — do not treat the persisting slot as evidence the content is UNCHANGED, and do not treat this the same as the unit being absent outright (the row above) — the two are different facts about the document set. |
| A document's own stated relationship between two units (e.g. "replaces," "supersedes," "restates") | Never accept a document's own characterization of how one unit relates to another as authoritative. Map both units by content independently first (Module 2, stage MAP); only report the relationship the content actually supports. A unit stated to "replace" another may in fact be REMOVED + ADDED (two independent, substantively different units) rather than one CHANGED unit, if their actual wording does not describe the same obligation. |
| A field or cell holds a placeholder, blank, or zero value in one version and a real value in the other | This is CHANGED, not ADDED — a counterpart unit exists (the field or cell itself), it simply held a placeholder/blank/zero value on one side. ADDED is reserved for a unit with no counterpart at all. This is the mirror image of the row above ("a unit's slot persists but its content is emptied or replaced"): there, real content is replaced by emptiness; here, a placeholder is replaced by real content — both are CHANGED because the slot/unit itself persisted throughout. |
| Multiple supporting/reference documents, or more than two versions | Apply the same pairwise logic between each version and its immediate predecessor (or against whichever version the run's config designates as the baseline for that unit); do not merge multiple documents' evidence into a single verdict without stating which document each side of the quote came from. |
| Mixed or converted formats (PDF vs. Word vs. spreadsheet vs. plain text) | Normalize both documents to extracted text (per the run's `actuals/twin/` process) before applying grain and verdicts — comparison operates on that normalized text, not on format-specific rendering artifacts. Confirmed in practice across PDF and spreadsheet (`.xlsx`) samples; this row requires no per-format skill logic, only a format-appropriate twin-extraction unit (a page, a sheet, a slide, a row) chosen at the orchestration layer, per `Bootstrap.md` §1/§12. |
