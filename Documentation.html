1. Overview

What this framework is, in short.

Bootstrap.md is a shared, use-case-agnostic execution framework for processing a source document against a supporting document. It never contains judgment logic, sample facts, or hardcoded paths itself — every concrete detail (which documents, which use case, which skill) is resolved at execution time from FileIndex.md, and every judgment rule lives in that use case's own skills/<usecase>/Skill.md.

The same orchestrator supports any number of use cases side by side — a bid evaluation, a document version comparison, or any other "read a source against a reference and produce findings" task — without ever being edited for a specific one. Adding a use case means adding a FileIndex.md entry and a skill file; it never means touching Bootstrap.md.

4. Command reference

Every command is invoked manually, in CAPITAL LETTERS, and resolves against FileIndex.md at run time.

START composes 7 commands

Syntax: START or START <usecase> (name required once more than one entry exists in FileIndex.md)

Input: the resolved FileIndex.md entry (source path(s), supporting path(s), skill path)

Output: everything RESOLVE → NORMALIZE → JUDGE → ENHANCE-SKILL → REPORT → VALIDATE → MANUAL VALIDATE each produce, for every resolved source/supporting pair

Flow: Composes, in strict order: RESOLVE → NORMALIZE → JUDGE → ENHANCE-SKILL → REPORT → VALIDATE → MANUAL VALIDATE. ENHANCE-SKILL and MANUAL VALIDATE run every time, for every sample — not conditionally, not only when something new is found. This is part of START's own defined behavior, not a separate trigger.

MANUAL VALIDATE HITL sign-off

Syntax: MANUAL VALIDATE (no argument = every use case currently configured), MANUAL VALIDATE <usecase>, or MANUAL VALIDATE <usecase1> <usecase2> … for specific use cases. This is the one command where a missing argument means "act on all," not the single-entry default or an <UNRESOLVED> block.

Input: already-generated twin/findings/report artifacts under actuals/, findings/, reports/ for each in-scope source document. It never generates, judges, or alters findings itself.

Output: a HITL validation record appended to HITL/<usecase>/<source-document-name>/MANUAL_VALIDATE.md:

Reviewer      : <reviewer name>
Validation    : MANUAL VALIDATE
Status        : VERIFIED
Date          : <execution-date>
Time          : <execution-time>
Use Case      : <use-case-name>
Document      : <document-name>

Flow: For each use case in scope, for every resolved source/supporting pair carrying generated output: (1) review the twin/findings/report artifacts, (2) mark as reviewed without editing their content, (3) append a new record to that document's MANUAL_VALIDATE.md — never overwrite, so it stays an auditable history oldest→newest, (4) log the invocation in that use case's own PromptLog. When composed by START, scope is always the single use case/sample START just processed.

RESOLVE

Input: FileIndex.md

Output: a confirmation per resolvable source/supporting pair, or <UNRESOLVED: reason> blocking only the failing pair(s)

Flow: selects the entry (implicit if exactly one; otherwise requires a use-case-name argument) → confirms all four fields are set and every path exists → confirms use_case_name matches the skill file's parent directory → confirms list-valued paths pair correctly per §2. First step of every run.

NORMALIZE

Input: resolved source + supporting documents

Output: actuals/<usecase>/<source-document-name>/ — twin extraction (per page/sheet/slide/row/record), derived read-through, section map, Detection.md, Plan.md

PLAIN

Input: resolved source document

Output: actuals/<usecase>/<source-document-name>/twin/ only — a raw extraction pass

Flow: stops before detection, planning, or judgment. Controls how much of the pipeline runs, not how extraction is done for a given format.

JUDGE

Input: actuals/<usecase>/<source-document-name>/Plan.md + the resolved skill

Output: findings/<usecase>/<source-document-name>/<unit>.md and actuals/.../Graph.md

OBSERVE

Output: an entry in skills/<usecase>/PatternLog.md — records a noticed pattern without changing the live skill.

ENHANCE-SKILL

Input: the current sample's findings + the live skill + PatternLog history

Output: a new skills/<usecase>/skill-versions/v<N>.md snapshot (if promoted) + an updated live Skill.md with a bumped version field

Flow: analyze sample against skill → log every observation in PatternLog.md → check each against the promotion bar (§8.2) → for promoted observations, generalize into the skill (never append raw sample context) → validate the change against all previous samples before considering it complete.

REPORT

Input: findings/<usecase>/<source-document-name>/ (that document's findings only)

Output: reports/<usecase>/<source-document-name>/Report.md

VALIDATE

Input: manifest/<usecase>/Manifest.md's checklist, cross-checked against FileIndex.md and PromptLog.md

Output: an updated verdict for that document in Manifest.md

SKILL CHANGE <version_number>

Syntax: SKILL CHANGE <version_number> — the version number is always supplied, never hardcoded

Output: a read-only report of that version's rules, how they differ from the version before it, and which existing findings were produced under it vs. a later version. Re-enters the pipeline partway through — it reads already-generated findings rather than regenerating them.

EXPORT

Input: the export-directory value in Bootstrap.md's own front matter

Output: a full copy of that directory, structure preserved exactly, including every use case's isolated subtree

Flow: bypasses document resolution entirely — operates on the configured directory as a whole, not per use case.

EXPORT
  ↓
Read export directory from Bootstrap.md front matter
  ↓
Resolve configured directory
  ↓
Collect complete directory contents
  ↓
Preserve directory structure
  ↓
Export the full directory
LOG

Output: a full-detail entry prepended to prompt-log/<usecase>/PromptLog.md. Invoked after every command that creates or changes a file.

5. file-index.md & multiple use cases

One entry per use case; exactly four fields each.

FileIndex.md is a list of entries. Each entry provides exactly use_case_name, source_document_path, supporting_document_path, and skill_file_path — nothing else. use_case_name is the unique key; two entries never share one.

List-valued paths and pairing rules

ShapeBehavior
Single source + single supportingOne document pair — the original shape
List of sources + single supportingThe one supporting document broadcasts to every source in the list
List of sources + list of supporting, same lengthPositional pairing — 1st with 1st, 2nd with 2nd, and so on
List of sources + list of supporting, different non-1 lengthsConfiguration error — <UNRESOLVED: source/supporting path counts do not pair (N vs. M)> for that entry

Every resolved pair runs the pipeline independently, into its own <source-document-name> subdirectory. A bad path blocks only its own pair — it never blocks other resolvable pairs in the same entry.

Selecting an entry when several exist

Exactly one entry in FileIndex.md → every command resolves against it, no argument needed.

More than one entry → a command that needs one use case requires its name as an argument (e.g. START bid-evaluation). Omitting it blocks with <UNRESOLVED: multiple use cases configured; specify which one> — never a silent default to "the first entry" or "the last-edited entry."

Exception: MANUAL VALIDATE with no argument means "every configured use case," not "the lone entry" — the one command where "no argument" means "all."

6. How Bootstrap.md controls the workflow

Orchestrator only — never a holder of use-case-specific logic.

Bootstrap.md defines commands, roles, and directory structure that hold regardless of use case or sample. If it ever contains judging logic, verdict definitions, or domain rules, that is treated as a defect to be moved into the applicable skill.

Amending Bootstrap.md (§11)

Changes rarely, and only when justified by something true across every use case — never by one sample's needs. Every amendment is recorded in the PromptLog of whichever use case's run prompted it (or the most recently active use case's log, if none did), with what changed and why.

Non-negotiable rules, grouped

GroupRules
Authority & scopeBootstrap.md is root authority for orchestration but holds no use-case logic; only FileIndex.md-configured documents are ever processed; no command runs automatically — every invocation is explicit
Skill integrityA skill changes only via the promotion bar + versioning procedure; historical skill-versions snapshots are immutable; Skill.md is the only live copy; every sample enhances the same skill, never a per-sample fork; every enhancement must still read true for a sample nobody has seen and remain valid for every prior sample
TraceabilityEvery generated artifact records its skill + version; every file-creating/changing event is logged as a new entry prepended to that use case's own PromptLog
Absence & uncertaintyAbsence is always the use case's defined label, never inferred or silent; when uncertain whether something is use-case-agnostic or specific, treat it as specific until the promotion bar is met
IsolationEvery generated root is scoped first by <usecase>, then by <source-document-name> — nothing is ever mixed, shared, or merged across use cases; every use case's directory shape is structurally identical, only content differs
OnboardingA new document/use case is onboarded by adding files and pointing FileIndex.md at them — never by deleting or overwriting another's files, never pre-templated
Format & namingNo file format is rejected or privileged; every generated .md filename follows CamelCase (except identifiers mirroring a real document's own name)
ExportEXPORT's scope is always the configured export-directory — never a hardcoded or assumed path

7. Skill files & versioning

Skill.md is the only live copy; every version is preserved forever.

skills/<usecase>/Skill.md holds verdict/label scales, the grain of judgment, absence handling, and required output shape — phrased to hold for any document pair in that use case. It never contains a business name, document title, or example lifted from one sample as if universal.

The promotion bar (§8.2)

An observation in PatternLog.md may be promoted into the live skill only when at least one holds:

ConditionMeaning
Cross-sample confirmationThe same pattern was independently observed in 2+ samples that don't share an author, template, or origin
Explicit generalization by the userThe user directly states the rule should apply beyond the current sample
Structural necessityThe pattern follows from the use case's own definition regardless of sample count

A single sample's structure, numbering scheme, or business terms are never, by themselves, sufficient.

Version-bump procedure (§9)

1. Snapshot current Skill.md → skill-versions/v<N>.md (immutable from that moment)
↓
2. Edit live Skill.md in place, bump front-matter version to <N+1>
↓
3. Validate against every previous sample (§8.4), then log the change in PromptLog.md

Non-material edits (typos, wording clarity with no behavior change) don't require a version bump but are still logged.

Example front matter

---
skill: <usecase>
version: <N>
status: current — live copy; snapshot preserved at skills/<usecase>/skill-versions/v<N>.md
supersedes: v<N-1>.md (see skills/<usecase>/skill-versions/ for immutable history)
title: <use case title>
intent: <what this skill reads and judges>
shape: <output shape, e.g. RANKED_COMPARISON>
grain: <the unit judged, e.g. one bidder / one page pair>
absence-policy: <how "not stated" is reported>
---

8. Prompt logging

Every file-creating or file-changing event, logged in full, at the time it happens.

prompt-log/<usecase>/PromptLog.md is maintained in descending chronological order — newest entry always at the top, directly under the header. New entries are always prepended, never appended below older ones. Each use case keeps its own complete, independent history — logs are never merged across use cases.

Required fields per entry

FieldContent
timestampDate and time the event happened
command/promptThe command or prompt provided
generated_outputWhat was produced
reasonWhy this output was generated
explanationBrief account of how the output was generated
modelThe model used
skill/version_usedThe relevant skill and version
other_metadataAny other detail needed to reproduce or understand the result

A required item that doesn't apply is still written — as "not applicable" with a one-clause reason — never simply omitted.

9. HITL / manual validation workflow

A human reviewer's sign-off, recorded without ever touching the underlying content.

HITL/<usecase>/<source-document-name>/ holds one MANUAL_VALIDATE.md per document — an append-only record of every manual validation performed for it, oldest to newest. Running MANUAL VALIDATE again for an already-validated document adds a new record; it never overwrites the previous one.

Record shape

Reviewer      : <reviewer name>
Validation    : MANUAL VALIDATE
Status        : VERIFIED
Date          : <execution-date>
Time          : <execution-time>
Use Case      : <use-case-name>
Document      : <document-name>

How it gates acceptance (§15)

No artifact is an accepted deliverable until all of:

1Its Manifest.md checklist is fully checked for the current sample
2Any skill change it depended on is versioned per §9
3Its PromptLog.md entries are complete
4HITL review is complete wherever required

In Manifest.md, a document's Governance block records state, signed-by, verified-by, and verified-on — filled in once the corresponding MANUAL_VALIDATE.md record exists, never before. A document's underlying content is never edited to reflect its review status — the HITL record is the only evidence of review.

11. End-to-end execution flow

One START run, from invocation to accepted deliverable.

1. Invoke START (or START <usecase> if FileIndex.md has more than one entry)
↓
2. RESOLVE — read FileIndex.md, select the entry, confirm every path exists and use_case_name matches the skill's directory
↓
3. NORMALIZE — extract the twin, derived read-through, section map, Detection.md, Plan.md for each resolved pair
↓
4. JUDGE — apply the live skill to every planned unit, write findings + Graph.md
↓
5. ENHANCE-SKILL — compare sample against the skill, log observations, promote what clears the bar, version-bump if warranted
↓
6. REPORT — assemble Report.md from this document's findings only
↓
7. VALIDATE — run the Manifest.md checklist, record a verdict
↓
8. MANUAL VALIDATE — human reviewer signs off; appends a record to HITL/…/MANUAL_VALIDATE.md
↓
9. Manifest.md's Governance block updates (state, signed-by, verified-by/on) — document becomes an accepted deliverable once §15's four gate conditions are all met

Every step along the way is logged as its own prepended entry in that use case's PromptLog.md (§10).
